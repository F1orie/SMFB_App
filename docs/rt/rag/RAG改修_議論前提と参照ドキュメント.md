# RAG改修 議論前提と参照ドキュメント

## 目的

次に行うRAG/AIフィードバック改修について、議論の前提をそろえるための整理です。

現時点で決まっていること、追加で決める必要があること、実装前に参照すべき `docs/` 配下のドキュメントをまとめます。

## 決定済みの方針

現時点で決まっている方針は次の3点です。

1. SQLiteに保存された睡眠データを参照する。
2. Chromaに保存された商品データを参照する。
3. プロンプトの設定ファイルはコードから分離する。

この方針から、FB/RAG改修の中心は「Flutter内で完結していたGemini直接呼び出し」を見直し、睡眠データ、商品データ、プロンプトテンプレートを組み合わせて回答を生成する構成へ移すことになります。

## 想定される新しい責務分担

### Flutter側

Flutter側は主に次を担当します。

- SQLiteから睡眠データを読み取る。
- 対象セッション、睡眠エポック、メモ、行動フラグをRAG用のリクエストに整形する。
- バックエンドのRAGエンドポイントへHTTPリクエストを送る。
- 返ってきたアドバイスを既存UIに表示する。

既存UIを大きく変えない場合でも、`FbDashboardPage` と `FbChatDialog` の内部処理は変更対象になります。

### Pythonバックエンド側

Pythonバックエンド側は主に次を担当する想定です。

- Flutterから受け取った睡眠データを要約する。
- Chromaの商品データを検索する。
- 分離されたプロンプト設定ファイルを読み込む。
- 睡眠要約、商品候補、ユーザー質問、チャット履歴を使ってプロンプトを構築する。
- GeminiなどのLLMを呼び出す。
- 生成結果をFlutterへ返す。

既存の `lib/features/fb/backend/main.py` はFastAPI + OpenAIの別系統実装として存在しますが、現行Flutter実装からは呼ばれていません。RAG用バックエンドとして使う場合は、構成を改めて決める必要があります。

## 議論で先に決めるべきこと

### 1. RAG処理の配置

現時点の既存仕様書では「PythonバックエンドがRAG処理を一元管理する」方向が書かれています。

この方針を採用する場合、FlutterはChromaへ直接アクセスしません。FlutterはSQLiteから睡眠データを取り、Pythonへ渡します。PythonがChroma検索とLLM呼び出しを担当します。

確認事項:

- RAG処理はPythonバックエンドに集約するか。
- FlutterからGeminiを直接呼ぶ処理は廃止するか。
- Flutter側に残すAI関連設定はバックエンドURLだけでよいか。

### 2. SQLiteの参照範囲

「SQLiteに保存された睡眠データを参照する」ことは決まっていますが、どのデータまでRAG入力に含めるかは決める必要があります。

候補:

- `SleepSession`: 就寝時刻、起床時刻、アラーム時刻、ステータス
- `SleepEpoch`: `activityCount`、`scoreDepth` の時系列
- `SleepNote`: メモ、アルコール、カフェイン、運動
- 行動データ: 食事、喫煙、入浴など。現状は `action_selections` にあり、正式モデルには入っていない
- 過去数日分の睡眠データ
- 対象セッション1件だけ

議論ポイント:

- RAGへ送る睡眠データは直近1件か、直近7日などの期間指定か。
- `SleepEpoch` の全件を送るか、要約して送るか。
- 行動データを `SleepNote` に残すか、別テーブル化するか。
- 1日に複数セッションがある場合の扱い。

### 3. Chromaの商品データ仕様

Chromaを参照することは決まっていますが、`docs/` 内に商品データの専用仕様はまだ見当たりません。

新たに決める必要がある項目:

- Chromaのコレクション名
- 商品データのスキーマ
- 商品カテゴリ
- embeddingモデル
- 検索クエリの作り方
- 検索件数
- 商品名、説明、URL、価格、カテゴリなど、プロンプトへ渡す項目
- 寝具、食べ物、ルーティンなどのアドバイス種別と商品カテゴリの対応

商品データがRAGの品質を大きく左右するため、SQLite移行とは別に「Chroma商品データ仕様」を作る必要があります。

### 4. プロンプト設定ファイル

プロンプトをコードから分離することは決定済みです。

既存仕様では `backend/prompts/fb_prompts.json` 案があります。

決めるべきこと:

- JSON、YAML、Markdownのどれで管理するか。
- プロンプト設定ファイルをPythonバックエンド配下に置くか。
- advice typeごとに system / user_template を分けるか。
- テンプレート変数をどう定義するか。
- プロンプトのバージョン管理をどうするか。
- プロンプト変更後、AIキャッシュを無効化するか。

最低限必要なテンプレート変数候補:

- `{sleep_summary}`
- `{sleep_epoch_summary}`
- `{lifestyle_notes}`
- `{product_suggestions}`
- `{query}`
- `{chat_history}`

### 5. 既存キャッシュの扱い

現状のFB機能は `SharedPreferences` にAI結果をキャッシュしています。

- `fb_ai_advice_<sessionId>`
- `fb_special_<type>_<sessionId>`
- `fb_chat_history_<sessionId>`

SQLite、Chroma、プロンプト設定ファイルを使うようになると、同じ `sessionId` でも入力条件が変わります。

議論ポイント:

- AIキャッシュを残すか、RAG化で一旦廃止するか。
- 残す場合、`input_hash` を持つか。
- 睡眠データ変更、商品データ更新、プロンプト変更でキャッシュを無効化するか。
- チャット履歴をSQLiteへ移すか。

## 次の議論で決める順番

おすすめの議論順は次の通りです。

1. RAG処理をPythonバックエンドに集約するか確定する。
2. FlutterからPythonへ送る睡眠データの範囲を決める。
3. Chromaの商品データスキーマを決める。
4. プロンプト設定ファイルの形式と配置を決める。
5. RAG APIのリクエスト/レスポンスを確定する。
6. SQLite移行を「読み取り先行」から始めるか、「保存先切り替え」まで一気に行うか決める。
7. 既存AIキャッシュとチャット履歴の扱いを決める。
8. 実装フェーズを切る。

## 現時点の推奨方針

既存ドキュメントと現状実装を見る限り、最初は次の方針が安全です。

1. `rag_system_spec.md` のB案、つまりPythonバックエンド集約を採用する。
2. SQLiteはまず読み取り基盤とダミーデータから作る。
3. Chromaはモック商品検索なしでAPI疎通を先に作り、その後に統合する。
4. プロンプト設定ファイルはPython側に置く。
5. Flutterの既存UIは維持し、内部通信だけを `ApiClient.chat()` からRAG APIへ差し替える。
6. AIキャッシュはRAG化の初期段階では無効化または一旦使わない。

この順番なら、既存のアラーム・グラフ・リスト機能を壊すリスクを抑えながら、RAGの動作確認を先に進められます。
